# BACKEND REQUIREMENT FOR MADA

## المرحلة الأولى: الوصول للبوث

- آلية تحقق رمز الوصول على السيرفر، ونتيجة نجاح أو رفض يمكن للواجهة عرضها.
- آلية إنشاء جلسة البوث والتحقق من صلاحيتها وانتهائها، مع توضيح طريقة استدعائها من الواجهة.
- تمييز رفض الرمز عن تعذر الاتصال أو تعذر الخدمة، حتى تعرض الواجهة استجابة مناسبة.

واجهة AccessService محلية ومؤقتة؛ لا تفرض شكل API أو رموز الأخطاء أو طريقة الجلسة. لا توجد مسارات نهائية مفترضة. الرمز الحقيقي وأي أسرار تبقى خارج كود العميل وNEXT_PUBLIC_*.

## المرحلة الثانية: المشارك

- تسجيل مشارك بالاسم الكامل ورقم تعريفي نصي، واسترجاعه بالرقم؛ دون تحويل الرقم إلى عدد أو فقد الأصفار الأولى.
- التحقق النهائي من البيانات على السيرفر، وإرجاع حالة واضحة للرقم المكرر أو غير الموجود، دون استبدال بيانات موجودة عند التكرار.
- اعتماد توحيد الأرقام العربية والفارسية، وسلوك إعادة التسجيل بعد تعذّر الاتصال، ضمن عقد الخدمة النهائي.

المحاكاة الحالية محلية فقط، ولا تقرر أهلية المشاركة أو القسم أو جدول الألعاب.

## المرحلة الثالثة: الأهلية والجدول

- توفير اليوم الفعلي وقسم المشارك/البوث من مصدر معتمد، وجدولين منفصلين يحددان اليوم الاستثنائي وخياري الطالبات. أسماء الألعاب والتواريخ لم تُعتمد بعد.
- إرجاع الألعاب المتاحة وأسباب المنع والنتائج المكتملة المعتمدة ومجموعها. السيرفر يطبق لعبة واحدة يوميًا وكل لعبة مرة طوال الفعالية، ويتعامل مع المحاولة قيد التنفيذ.
- إعادة التحقق من الأهلية بصورة نهائية عند اعتماد Start لاحقًا لمنع التعارض بين أجهزة البوث؛ تأكيد الاختيار في المرحلة الثالثة لا يحجز محاولة.

EligibilityService نموذج احتياجات الواجهة فقط. لم يُعتمد مسار API أو بروتوكول Start، ولم يُنفّذ Backend.

## المرحلة الرابعة: بدء المحاولة وتشغيل اللعبة

- اعتماد Start بعد إعادة التحقق من الأهلية، ومنع الحجز المكرر/المتزامن وتحديد آلية آمنة لإعادة الطلب. معرّف الطلب الحالي مثال Mock وليس فرضًا لعقد السيرفر.
- توفير حالة المحاولة النشطة للمشارك للاستعادة عند فقد رد البدء أو العودة/تحديث الصفحة، دون اعتبار العودة للبوث إنهاءً للمحاولة.
- الاتفاق على التعامل مع المحاولة غير المكتملة، وصلاحية إعادة التحكم لعضو النادي. لا توجد سياسة إلغاء مفترضة في الواجهة.
- الاتفاق مع الأقسام على تكامل HTML المحلي وإشارات الجاهزية والانتهاء ومتطلبات sandbox، قبل اعتماد Game SDK. إشارة الجاهزية الحالية داخلية لصفحة اختبار فقط.

لا تُرسل نتيجة متصفح ولا يُسجّل اكتمال في هذه المرحلة.


## BACKEND REQUIREMENT FOR MADA — المرحلة الخامسة

- حفظ نتيجة معرّفة بالمحاولة مرة واحدة، مع إعادة إرسال آمنة ومنع تعارض النقاط، وإنهاء المحاولة وتحديث الأهلية في نفس العملية.
- استعلام حالة الحفظ بمعرّف المحاولة يعيد النتيجة المعتمدة أو عدم الحفظ؛ تعذر الاستعلام لا يُفسر كعدم حفظ.
- تحديد مصدر النتيجة الموثوق والتحقق من حدودها على السيرفر، والاتفاق مع الأقسام على إشارة انتهاء اللعبة. زر 80 الحالي أداة Mock فقط.
- استعادة حالة المحاولة/النتيجة بعد انقطاع الصفحة ضمن جلسة عضو النادي. أسماء الأنواع الحالية مسودة واجهة وليست API مفروضًا.


## المرحلة السادسة: المتصدرون والربط

- توفير أفضل ثلاثة بحسب مجموع النتائج المعتمدة، مع اسم العرض والنقاط وعدد الألعاب وترتيب معتمد؛ تأكيد سياسة التعادل ونطاق القائمة (عام أم منفصل لكل قسم).
- اعتماد أسماء العرض المسموح إظهارها دون الرقم التعريفي، وآلية تحديث القائمة.
- لاستبدال Mock: توثيق الاستدعاءات الفعلية، عنوان بيئة الاختبار، طريقة الجلسة وانتهائها، وأمثلة النجاح والفشل. لا تُرسل مفاتيح خادم سرية للواجهة.
- أفاد صاحب المشروع بأن Backend جاهز وسيزوّدنا بتفاصيل الربط. حتى وصولها يظل الربط الحقيقي معلّقًا؛ لا توجد مسارات أو جلسات إنتاجية مفترضة.

ترتيب Mock الحالي عام ومؤقت: مجموع تنازلي، رتب مشتركة للمتعادلين، وثلاثة أسماء كحد أقصى؛ التعادل عند حد الثلاثة يحافظ على ترتيب الإدخال ولا يحسم فائزًا إنتاجيًا.


## تحديث الربط في الواجهة — 2026-11-12

وصل عقد API ونُفذت المحولات وإدارة جلسة الساعة واستعادة الحفظ عبر progress. لم نحتج إضافة endpoints أو service-role key. ما يزال مطلوبًا اعتماد جدول الأقسام وملفات الألعاب ومصدر النتيجة، وتوافق الأرقام وسياسة المحاولات القديمة والمتصدرين. التقرير السابق مراجعة تاريخية، والحالة الحالية في backend-integration.md.
