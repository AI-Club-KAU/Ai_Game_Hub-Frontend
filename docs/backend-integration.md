# ربط Backend — الحالة الفعلية

## Phase 7D-1 — واجهة ترتيب الألعاب، بانتظار نشر API

صفحة واحدة بستة تبويبات: Overall وESCAPE.EXE وDev Run ووصّل طريقك وGame 4 وGame 5. يبقى Overall على GET /leaderboard بحد ثلاثة ومجموع أقصى 500، دون تغيير عقده أو ترتيب الخدمة أو سياسة التعادل الحالية.

العقد المعتمد المستقبلي هو GET /leaderboard/games/{game_id} باستعمال المصادقة الحالية. يتضمن game_id الرقمي وmax_score=100 وleaderboard حتى عشرة صفوف من full_name وscore الصحيح 0–100 بترتيب تنازلي. يفحص backend-game-leaderboard-service.ts الهوية والحدود وشكل البيانات والترتيب؛ لا يصحح أو يقتطع ردًا غير صالح. تُعرض المراكز وفق ترتيب API، بما فيه ترتيب التعادل الذي يقرره السيرفر. لا يوجد حقل كسر تعادل إضافي معتمد، ولا تُخترع معرفات أو قواعد ترتيب بالأسماء.

النشر غير مؤكد: تهيئة التطبيق في services/index.ts لا تمرر deploymentConfirmed، ولذلك تبقى خدمة ترتيب الألعاب في Live معطلة حتى اعتماد تغيير صريح بعد تأكيد Mada. اختيار تبويب لعبة يعرض حالة الانتظار دون أي طلب Backend. اختبارات العميل وحدها تفعّل المسار مع transport محاكى. لا متغير بيئة جديد يفعّله، ولا تفعيل تلقائي بناءً على عنوان الوجهة.

في Mock تعرض تبويبات الألعاب أمثلة UI مستقلة وموسومة بوضوح، أو حالات فارغة/خطأ؛ لا تُحوّل سجلات QA 2 أو3 إلى Dev Run أو وصّل طريقك، ولا تتغير هويات الكتالوج أو نتائجه أو تجميع Overall. وضع النتائج المحفوظة لا ينتج ترتيبًا وهميًا للألعاب الحقيقية. تبويبا 4 و5 لا يتيحان اللعب، وتظل أصولهما محجوبة في Live.

الاختبارات محلية ومعزولة: التبويبات والهواتف ولوحة المفاتيح وحالات العرض، وحد العشرة واتساق الرد وهوية اللعبة ومسارات 1–5 والمصادقة وتجديدها، ومنع استدعاء المسار الجديد في Live. لا اتصال بـSupabase أو Google. يلزم لاحقًا تأكيد Mada لنشر المسار في البيئة المقصودة وعقده والمصادقة وCORS وسياسة التعادل قبل تفعيله؛ دعم top 10 لا يعد تحققًا من نشر Backend.

تم تنفيذ الربط بعقد ../devweek-backend/docs/api.md. الوضع والعنوان يتطلبان إعدادًا صريحًا؛ لا يوجد عنوان Live افتراضي.

## الوصول

رمز البوث يُدخل وقت التشغيل إلى /access/verify للحصول على token لمدة ساعة. الواجهة لا تستخدم SUPABASE_SERVICE_ROLE_KEY ولا تحتفظ برمز الدخول أو token في التخزين أو عنوان URL. لا يلزم apikey أو SDK.

التوكن في الذاكرة ويُمسح بقفل البوث أو إعادة التحميل. عند انتهاء الجلسة يظهر نموذج تجديد، مع إخفاء المحتوى السابق دون تفكيكه للحفاظ على سياق المحاولة. إعادة الطلب تلقائيًا مقتصرة على 401 invalid_platform_token بعد التجديد، لأن المصادقة تُرفض قبل أي كتابة في معالج الباك إند؛ لا إعادة آلية عند فقد الشبكة أو 500.

## محولات API الموجودة

الجدول التالي يصف محولات Backend المنفّذة. ESCAPE.EXE مرتبطة بها في Live بالمعرّف الرسمي 1، وتبقى mock في Mock. التحقق المحلي يستخدم استجابات محاكية ولا يثبت نجاح الرحلة على Supabase الفعلي.

| الوظيفة | المسار | السلوك |
| --- | --- | --- |
| الوصول | POST /access/verify | token في الذاكرة |
| المشاركون | POST /students/register و /students/login | UUID داخلي مع إبقاء الرقم النصي والأصفار |
| الأهلية | GET /students/{id}/progress | التاريخ وقرار الأهلية والنتائج من السيرفر؛ يتضمن أسماء الألعاب فلا يلزم طلب /games إضافي |
| البداية | POST /attempts/start | حقول student_id وgame_id فقط؛ لا retry آلي |
| الاستعادة | GET progress | جميع المحاولات started، دون إلغائها أو حسم سياستها |
| النتيجة | POST /attempts/finish وGET progress | قراءة الحالة قبل الكتابة؛ استعادة 409 والرد المفقود دون تكرار |
| المتصدرون | GET /leaderboard | الحفاظ على ترتيب الخدمة دون تصفية أو إعادة حسم التعادل |

النتيجة المعتمدة هي attempt.score مع completed وscore_saved=true. تعذر المجموع لا يلغي حفظ النقاط. الكسر أو درجة خارج 0–100 لا تُرسل. إذا تعذر الاستعلام عن حالة الحفظ يبقى غير محسوم ولا تبدأ مهلة العودة.

## قيود التشغيل الحالية

- تحقّق Live الدفاعي يرفض كتالوجًا يتجاوز خمس ألعاب أو يكرر معرفًا، والمعرفات المقبولة أعداد صحيحة من 1 إلى 5 وحد كل لعبة 100. المجموع يجب أن يكون عددًا صحيحًا من 0 إلى 500، وgames_completed إن ورد يجب أن يكون عددًا صحيحًا من 0 إلى 5؛ لم يصبح حقلًا إلزاميًا جديدًا. تُفحص درجات المحاولات المكتملة ضمن 0–100، وتبقى درجة started بقيمة null. لا نفرض تطابق المجموع وعدد الإكمالات مع تفاصيل الألعاب لحظيًا، لأن عقد progress المحلي يذكر أن القراءات ليست snapshot واحدة.
- لا يُرسل Start إلا لمعرّف نصي قياسي من 1 إلى 5؛ تُرفض mock والأرقام غير القياسية أو غير الصالحة قبل أي اتصال. عند تأكيد Finish أو استعادته عبر progress تُطابق هوية المحاولة والمشارك واللعبة مع السياق المعروف، ولا يُعاد ربط محاولة معروفة بلعبة أخرى. تعتمد هذه المطابقة على الحقول الموجودة بالفعل؛ لا تثبت صحة اللعب أو ملكية المشارك، ولا تغني عن ضمانات Backend الذرّية.

- game-assets.ts يفصل الوضعين صراحةً: ESCAPE.EXE بالمعرّف mock في Mock وبالمعرّف الرسمي 1 في Live. أصول QA ذات المعرّفات 2–5 تستخدم public/games/container-check/ في Mock فقط؛ لا يغيّر الربط هويات Mock أو سجلاته القديمة.
- الأصول الحية المعتمدة هي ESCAPE.EXE بالمعرّف 1 وDev Run بالمعرّف 2 ووصّل طريقك بالمعرّف 3. ألعاب 4–5 محجوبة عن البدء والاستئناف في Live. زر نتيجة 80 مخصص لأصول QA في Mock؛ لا يظهر مع ESCAPE.EXE أو في Live.
- تُفعّل مصافحة المضيف وضع المنصة، وتُستقبل robomaze:result مع payload.finalScore بعد التحقق من المصدر وorigin=null ورمز الجلسة واتساق الإجابات. تُحفظ الدرجة عبر resultService للوضع المحدد، وتبقى شاشة النهاية ظاهرة مع منع الإعادة. بعد تأكيد الحفظ وعدّ 10 ثوانٍ يعود المشارك نفسه إلى اختيار الألعاب وتُحدّث حالته.
- في Live يُرسل Start مرة واحدة للعبة 1. الاستئناف يقرأ المحاولة started من progress ويفتح iframe جديدًا بنفس attempt_id دون Start آخر؛ لا تُستعاد حالة اللعب. Finish يستخدم محاولة Backend نفسها. لم تُختبر الرحلة الفعلية على Supabase بعد.
- بقية ألعاب الأقسام تحتاج تسليم أصولها واعتماد الجاهزية وإشارة النهاية ومصدر النقاط قبل ربطها. تفاصيل مصافحة ESCAPE.EXE وحماية الإعادة في docs/game-integration.md؛ نجاح Mock لا يثبت اعتماد Backend الحقيقي.
- أُلغي الجدول وحد المشاركة اليومية. يعتمد Frontend على eligible_to_start؛ يمكن إكمال الألعاب الخمس في اليوم نفسه.
- يُعرض كل started من progress. لم نغير سياسة الباك إند أو نفرض إلغاء/تحرير فرصة.
- الاسترجاع بعد تحديث الصفحة يبدأ بالتحقق من رمز البوث ثم رقم المشارك؛ تُحمّل محاولاته من progress. تقدم اللعبة داخل iframe لا يُحفظ تلقائيًا.
- الواجهة توحد الأرقام العربية/الفارسية وتقصر الرقم على أرقام. بيانات Backend الأخرى تحتاج قرار توافق قبل اعتمادها.
- الخدمة الحالية قد تعرض مسجلين بلا إكمال في المتصدرين، والتعادل مرتب بواسطة UUID؛ حافظنا على ترتيبها.

## الاختبارات وحدودها

اختبارات backend-services.spec.ts تتحقق من الطلبات الحقيقية الشكل عبر transport اختباري، وحالات ضياع رد الحفظ وفشل المجموع و409 والتحقق قبل إعادة الكتابة وتعدد المحاولات وانتهاء الجلسة وعدم تكرار Start.
اختبارات backend-ui.spec.ts تعترض الشبكة في المتصفح للتحقق من الدخول والاسترجاع والأهلية وتجديد الجلسة وعدم إرسال محاولات لأصول QA.

اختبارات escape-exe.spec.ts وescape-exe-results.spec.ts تغطي تشغيل ESCAPE.EXE ونتائجها في Mock، وbackend-escape-exe.spec.ts يغطي رحلة Live بعقد API محاكى: البدء والاستئناف وrefresh والنتائج والرسائل غير الصالحة وفقد الرد وحماية الهوية والعودة بعد تأكيد الحفظ. اختبارات QA تبقى مستقلة وتستخدم صفحة الفحص وزر نتيجة 80. لا تُحفظ نقاط اختبار على Supabase.

فحص Supabase المباشر الوحيد أثناء الربط: OPTIONS /students/login أعاد 204 مع CORS يدعم Authorization وContent-Type. لا يثبت هذا صحة رمز البوث أو نجاح الرحلة المصادق عليها.

لم يُستخدم مفتاح الخدمة، ولم تُرسل تسجيلات أو محاولات أو نقاط فعلية إلى Supabase. اختبار الدخول الفعلي يحتاج إدخال رمز البوث من صاحب المشروع في الواجهة. لا تعد اختبارات العقد بديلًا عن رحلة كاملة على بيئة اختبار مع ألعاب مسلّمة.

آخر تحقق: 9 اختبارات ربط نجحت، و28 اختبار Mock نجحت. نجح TypeScript وبناء الإنتاج النهائي بوضع live. خادم المعاينة النهائي يعمل بوضع live على http://localhost:3000.

## إعداد آمن وفصل بيئات الاتصال

- يجب تحديد NEXT_PUBLIC_API_MODE صراحةً: mock للمحاكاة أو live للخدمة. القيمة المفقودة أو الفارغة أو غير المعروفة تعرض خطأ إعداد وتمنع أي طلب Backend؛ لا يوجد وضع Live افتراضي.
- عند اختيار live يجب تحديد NEXT_PUBLIC_API_BASE_URL صراحةً لعنوان API المعتمد للبيئة المطلوبة. لا يوجد عنوان Production أو Staging افتراضي. اختيار live لا يثبت سلامة الاتصال بالخدمة.
- يقبل العنوان HTTPS، أو HTTP على loopback للاختبار المحلي فقط. تُرفض العناوين النسبية وبيانات المستخدم وكلمات المرور وquery وfragment والصيغ التي تتطلب تصحيحًا ضمنيًا. لا تظهر قيمة الإعداد في رسالة الخطأ.
- الإعداد الصالح لا يثبت أن الوجهة Staging؛ تؤكد Mada عنوان المشروع وعزل قاعدة بياناته والدوال والمهاجرات وCORS قبل أي اتصال فعلي.
- NEXT_PUBLIC_* تُدمج أثناء البناء. ابنِ Mock وStaging بصورة منفصلة؛ تغيير Runtime Environment أو إعادة تشغيل حزمة قديمة لا يغيّر وجهتها. أعد تشغيل خادم التطوير بعد تغيير الإعدادات.
- ملفات .env المحلية وإعدادات البناء الخارجية قد تغير الوجهة؛ راجع أولوية إعدادات Next.js. ملف .env.staging لا يُحمّل تلقائيًا كوضع مستقل، ولا تستخدم NODE_ENV=staging.
- لا تضع رمز البوث أو signing secret أو Service Role في أي متغير عام. يُدخل رمز الوصول في الشاشة فقط.

مثال PowerShell لبناء Mock:

~~~powershell
$env:NEXT_PUBLIC_API_MODE = 'mock'
pnpm build
~~~

لبناء Staging لاحقًا بعد اعتماد البيئة: اضبط NEXT_PUBLIC_API_MODE=live وNEXT_PUBLIC_API_BASE_URL إلى عنوان Edge Functions الذي تؤكده Mada ثم نفّذ build في مساحة منفصلة. لا تستخدم حزمة Mock نفسها ولا تنقل حزمة Production القديمة مع تغيير runtime فقط.

### اختبارات محلية بلا خدمات حقيقية

~~~powershell
$env:NEXT_PUBLIC_API_MODE = 'mock'
pnpm test
$env:NEXT_PUBLIC_API_MODE = 'live'
pnpm test
~~~

Playwright يفرض وضعًا صريحًا ويشغّل خادمًا محليًا جديدًا: 3101 لـMock و3102 لـLive، دون إعادة استخدام خادم قائم. عنوان API الاختباري وهمي على backend.invalid؛ لا يُستخدم عنوان المشغّل الحقيقي حتى لو كان موجودًا في البيئة.

الخادم يعمل على نسخة مؤقتة داخل tmp/ ولا ينسخ .env أو incoming-games أو مخرجات البناء. هذا يحمي next-env.d.ts الأصلي من تحديثات Next.js. عمليات Node محمية بحاجز loopback، والمتصفح يستخدم proxy محليًا لا يمرّر الاتصالات الخارجية، مع حظر Service Workers واعتراض الشبكة وWebSocket. الطلب غير المحاكى يُحظر ويُفشل الاختبار. تستخدم الحالات tests/fixtures بدل استيراد test مباشرة من @playwright/test، وللسياقات الإضافية تستخدم newIsolatedContext.

اختبارات Live تستخدم عنوان API الاختباري المركزي في tests/test-environment.ts، ولا تعتمد على hostname خاص بـProduction. فحوص العزل تتحقق كذلك من طلب API غير محاكى ومحاولة تجاوز الاعتراض. هذه اختبارات عقود وواجهة محلية، وليست اختبار تكامل Supabase.

لتحقق بناء معزول وآمن دون تعديل ملفات Next المولدة في الجذر:

~~~powershell
node scripts/run-isolated-next.mjs build mock
node scripts/run-isolated-next.mjs build live
~~~

كلاهما يستخدم إعدادًا وهميًا وحاجز شبكة Node؛ مخرجاتهما داخل tmp/ وليستا حزمتين للنشر إلى Staging.

تسجيل المشارك واسترجاعه يرفضان student_number المرتجع إذا لم يطابق الرقم المطلوب حرفيًا قبل تحديث الذاكرة؛ لا تُحذف أصفار ولا تُوحّد هويات مختلفة داخل المحول. يبقى تطبيع إدخال المستخدم الحالي في واجهة النموذج كما هو.

## Dev Run — Live game 2

Dev Run منشورة في public/games/dev-run/ من incoming-games/Dev--Run.zip. يبقى ZIP الأصلي وREADME المنسوخ دون تعديل؛ سجل البصمات والتغييرات في docs/dev-run-provenance.md.

تعمل في Live بالمعرّف 2 فقط. ESCAPE.EXE تبقى 1، وLive 4–5 محجوبة. كتالوج Mock لم يتغير: mock لـESCAPE.EXE و2–5 لأصول QA؛ لا يُعاد تفسير سجل QA 2 على أنه Dev Run.

مصافحة Dev Run هي ai-hub:dev-run-init بالإصدار 1، مع game=dev-run وnonce جديد وMessagePort. تُفحص نافذة الأب وأصلها وnonce المطابق للتحميل؛ معامل URL وحده لا يفعّل وضع المنصة. الجاهزية ai-hub:dev-run-ready والقفل ai-hub:dev-run-lock عبر MessageChannel. تبقى sandbox=allow-scripts دون allow-same-origin، ولا تدخل هوية المشارك أو attempt_id أو token إلى iframe.

في وضع المنصة ترسل DEV_RUN_FINAL_SCORE مع version وgame وnonce وscore وmaxScore=100 وstats وbreakdown. يتحقق dev-run-result.ts من الدرجة الصحيحة 0–100 ومن اتساقها مع ScoreManager.compute الأصلي: عناصر حتى 30، أسئلة حتى 50، مكافأة عدم الاصطدام 10 عند الإكمال، ومكافأة الإكمال 10. تُقفل أول نتيجة صحيحة تزامنيًا؛ attempt_id من المضيف فقط.

بعد الإكمال داخل المنصة يُمنع start وgoHome وresetSession وresume وinit وstartLoop ومسار تغيير الحالة من إعادة الجولة. تبقى شاشة النتيجة الأصلية ظاهرة، وتصبح غير تفاعلية، مع استمرار حفظ المنصة خارج iframe. التشغيل المستقل يحتفظ برسالة النتيجة القديمة والإعادة العادية.

المؤقت الأصلي 120 ثانية من اللعب، متوقف أثناء الأسئلة والإيقاف المؤقت؛ قد تتجاوز الجولة 180 ثانية فعلية. لا تفرض المنصة مهلة لعب جديدة. الاستئناف يفتح iframe وnonce جديدين من البداية وبنفس محاولة Backend، دون Start ثانٍ أو استعادة موضع.

تستخدم Start/Progress/Finish وخدمة النتائج واللوحة الموجودة: لا endpoints أو حقول Backend جديدة. يبدأ عد العودة لعشر ثوانٍ بعد تأكيد الحفظ فقط، ويعود المشارك نفسه مع تحديث أهليته. تحذير المغادرة لا يضمن استرداد درجة غير محفوظة بعد إغلاق الصفحة.

التحقق محلي فقط عبر عزل Phase 6B واستجابات Backend معترضة. tests/dev-run.spec.ts وtests/dev-run-results.spec.ts تغطيان الأصل والمصافحة والدرجات والإعادة والمؤقت؛ tests/backend-dev-run.spec.ts تغطي Start والاستئناف وrefresh وFinish وحالات عدم التأكد والعودة والمتصدرين. لا يعني ذلك التحقق من Supabase فعليًا.

قبل اختبار Staging: تؤكد Mada سجل اللعبة 2 وتفعيله وحده الأعلى 100، وتوفر البيئة المنفصلة والمهاجرات والدوال والمصادقة وCORS وعنوان API المعتمد. لا تُستخدم بيانات Production أو رموز فعلية في الاختبارات المحلية.

## وصّل طريقك — Live game 3 (Phase 7C-2)
