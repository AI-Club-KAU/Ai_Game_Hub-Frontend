# مراجعة جاهزية الربط — 2026-11-12

المصدر: ../devweek-backend. راجعت التوثيق، معالجات API، محولات التخزين، مخطط SQL، واختبارات الوحدة، وقارنتها بخدمات الواجهة الحالية. لم أعدّل Backend أو أربط الواجهة أو أرسل عمليات إلى Supabase.

## النتيجة

يمكن بدء بناء محولات الواجهة اعتمادًا على docs/api.md الموجود، لكن لا يمكن اعتماد التجربة كاملة وفق المتطلبات السابقة قبل حسم جدول الأقسام والمحاولات غير المكتملة. ليست كل الفروقات نواقص في Backend؛ بعضها تعديلات لازمة في Frontend.

## ما هو متوفر

- وصول برمز مشترك ينتج token صالحًا ساعة، وتسجيل/استرجاع مشارك برقم نصي وUUID.
- GET games وprogress، وStart وFinish، وleaderboard.
- قيود قاعدة البيانات تمنع تكرار اللعبة أو اليوم وتكرار حفظ النتيجة.
- progress يحتوي المحاولات المكتملة وغير المكتملة؛ يكفي أساسًا لاستعادة البدء والتحقق من حفظ النتيجة دون مطالبة مدى بمسار inspect جديد.
- finish يؤكد score_saved حتى إذا فشل جلب المجموع؛ لا حاجة لإعادة تصميم هذه الاستجابة.
- وثيقة API تتضمن عنوان الربط وطرق الطلب وCORS والأخطاء. لا نحتاج service-role key في الواجهة.

## 1. جدول الطلاب والطالبات وفترة الفعالية — مانع لمطابقة المتطلبات

المخطط لا يحتوي القسم أو الجدول أو تواريخ الأيام الخمسة. الأهلية في supabase/functions/_shared/game-api.ts:25 هي: لعبة نشطة، لا محاولة سابقة لها، ولا محاولة اليوم. Start في السطرين 47–48 يطبق القيود نفسها دون جدول. لذلك تكون الألعاب الخمس النشطة قابلة للاختيار قبل أول محاولة اليوم، ولا يوجد تطبيق لليوم الاستثنائي للطالبات أو منع خارج فترة الفعالية.

المطلوب من مدى بعد اعتماد بيانات الفعالية: مصدر موثوق للقسم واليوم والجدول، وتطبيقهما في progress وStart. لا يكفي إخفاء الألعاب في Frontend. لا نفرض مخطط جداول أو endpoint جديدًا.

## 2. المحاولات غير المكتملة — قرار سلوك قبل الربط

الباك إند يستهلك فرصة اليوم واللعبة عند Start حتى مع الانقطاع. ويتيح لعبة أخرى في اليوم التالي بينما تظل القديمة started؛ الاختبار tests/games.test.ts:75 يثبت ذلك. يمكن أن توجد عدة محاولات started للمشارك على أيام مختلفة.

الواجهة الحالية تتعامل مع محاولة نشطة واحدة وتمنع الاختيار بوجودها. نحتاج قرارًا: هل تبقى المحاولة القديمة قابلة للاستئناف لاحقًا، وكيف نعرض عدة محاولات؟ أم توجد سياسة أخرى؟ لا نفترض إلغاء أو تحرير فرصة، ولا نضيف endpoint إلغاء غير مطلوب.

## 3. الجلسة وهوية المشارك — عمل Frontend

- الاحتفاظ بالtoken في الذاكرة وإرساله مع الطلبات، ومسحه عند القفل.
- معالجة 401 أثناء اللعب/الحفظ بطلب رمز عضو النادي مجددًا دون فقد سياق المحاولة والنتيجة غير المؤكدة.
- الاحتفاظ بstudent.id بجانب الرقم النصي؛ النوع الحالي Participant لا يحمل UUID.
- ربط تواريخ play_date الحقيقية بالعرض، بدل اختلاق EventDay 1–5 أو قسم غير موجود.
- استعادة المحاولات عبر progress عند فقد رد Start؛ لا نرسل requestId الخاص بالـMock كحقل API غير موثق، ولا نعيد Start تلقائيًا.

## 4. تأكيد الحفظ — عمل Frontend

Mock يعيد النجاح عند إرسال النتيجة نفسها مجددًا. API الحقيقي يعيد 409 attempt_already_completed، حتى مع نفس النقاط. يجب أن يتحقق المحول عبر progress من المحاولة ذاتها ويعرض النقاط المحفوظة، دون افتراض فشل الحفظ أو محاولة أخرى.

التأكيد المباشر يحتاج score_saved=true ومحاولة completed. total_available=false لا يعني فشل حفظ النقاط، وnull ليس صفرًا. يبدأ مؤقت 10 ثوانٍ بعد تأكيد النقاط فقط. النتيجة integer 0–100؛ الـMock الحالي يقبل الكسور ويحتاج توحيدًا.

## 5. الرقم التعريفي — اتفاق بيانات

Frontend يسمح بأرقام فقط ويوحد العربية والفارسية ويزيل المسافات الخارجية. Backend يقبل أي نص غير فارغ ويحفظه حرفيًا، بما فيه المسافات والرموز والأرقام العربية.

يلزم اعتماد قاعدة موحدة؛ خصوصًا إذا توجد سجلات سابقة، إذ تحويل الرقم قبل البحث قد يمنع استرجاعها. لا تُغيّر أرقام موجودة أو تُرحّل بيانات تلقائيًا.

## 6. المتصدرون — قرار عرض

Backend يرجع حتى ثلاثة مرتبين بالنقاط ثم UUID، وقد يشمل مسجلين لم يكملوا أي لعبة (صفر ألعاب). Mock يعرض أصحاب النتائج المحفوظة فقط مع رتب مشتركة عند التعادل.

المطلوب: تأكيد إدراج/استبعاد من لم يكمل لعبة، ونطاق اللوحة العام أو المنفصل، وعرض التعادل. إن كان المطلوب استبعاد غير المشاركين، يجب التصفية قبل LIMIT 3 في الخدمة؛ حذفهم بعد استلام ثلاثة عناصر قد يعطي قائمة ناقصة. لا يستبعد أصحاب نتيجة صفر صحيحة مع games_completed>0.

## 7. ألعاب الأقسام — اعتماد قبل التشغيل الحقيقي

المشروع الحالي صفحة اختبار وزر نتيجة 80 فقط. نحتاج ملفات الألعاب وأسماءها وربطها بالمعرفات 1–5، وإشارة نهاية متفقًا عليها ومتطلبات sandbox. الباك إند يتحقق من نطاق النقاط لكنه لا يتحقق من اللعب نفسه؛ يلزم الاتفاق على مصدر النتيجة الموثوق دون فرض Game SDK أو مشروع حماية إضافي.
