# AI Club Games Hub

منصة ألعاب نادي الذكاء الاصطناعي لفعالية Dev Week، بواجهة عربية RTL لأجهزة البوث.

## الحالة الحالية

تمت إضافة محولات API للباك إند الموجود في devweek-backend. اختيار الوضع صريح دون افتراضي Live، ويستخدم وضع Live وظائف Supabase الموثقة دون SDK أو service-role key في الواجهة.

- الدخول يحتاج رمز البوث الحقيقي الذي يُدخل في الشاشة؛ demo يعمل فقط في وضع Mock.
- تُحفظ جلسة الساعة في الذاكرة، وعند انتهاء صلاحيتها تظهر شاشة تجديد تحتفظ بسياق الطلب والمحاولة.
- التسجيل، الاسترجاع، الأهلية، المحاولات، حفظ/استعلام النتائج والمتصدرون لها محولات API.
- ESCAPE.EXE مدمجة داخل حاوية iframe من public/games/escape-exe/: بالمعرّف mock في Mock، والمعرّف الرسمي 1 في Live. تستخدم خدمات الوضع المحدد للبدء والاستئناف بنفس المحاولة وحفظ الدرجة الفعلية، مع إبقاء شاشة النهاية والأنيميشن ومنع الإعادة بعد الإكمال داخل المنصة.
- في Mock، الألعاب ذات المعرّفات 2–5 هي أصول QA تستخدم public/games/container-check/؛ زر نتيجة 80 مخصص لهذه الأصول في Mock ولا يظهر مع ESCAPE.EXE أو في live.
- ESCAPE.EXE معتمدة في Live بالمعرّف 1 وDev Run بالمعرّف 2 ووصّل طريقك بالمعرّف 3؛ الألعاب 4–5 تظل محظورة حتى تسليم أصولها واعتمادها. ربط Start/Finish منفّذ ومختبر محليًا باستجابات API محاكية؛ لم تُختبر رحلة لعب ESCAPE.EXE على Supabase الفعلي بعد.
- تاريخ الرياض يُعرض للسجل فقط. تعتمد إتاحة كل لعبة على eligible_to_start؛ لا حد يومي أو جدول أقسام.
- رقم المشارك في الواجهة ما زال أرقامًا مع توحيد العربية/الفارسية؛ يجب الاتفاق على السجلات التي تحتوي صيغًا أخرى قبل استيرادها.

تفاصيل التشغيل والقيود: [docs/backend-integration.md](docs/backend-integration.md).

## تجربة ESCAPE.EXE — Mock فقط

1. فعّل NEXT_PUBLIC_API_MODE=mock وأعد البناء والتشغيل كما هو موضح في قسم «إعداد وضع الاتصال والاختبارات» أدناه.
2. ادخل بالرمز demo، ثم جهّز المشارك. يظهر كتالوج Mock الموحّد افتراضيًا؛ تغيير «سجل تجريبي» من «إعدادات العرض التجريبي» لا يغيّر هويات الألعاب.
3. اختر اللعبة وأكّد الاختيار وابدأ اللعب. عند الخروج قبل الإكمال يمكن استئناف نفس محاولة المنصة بجولة جديدة من البداية.
4. تُستقبل الدرجة الفعلية من robomaze:result في payload.finalScore، مع التحقق من المصدر والجلسة واتساق الإجابات. لا يُستخدم زر نتيجة 80 مع هذه اللعبة.
5. تبقى شاشة النهاية ظاهرة وتُعرض حالة الحفظ خارج iframe. بعد تأكيد الحفظ فقط يبدأ عدّ 10 ثوانٍ، ثم يعود المشارك نفسه إلى اختيار الألعاب مع تحديث نتيجته ومنع الإعادة. «تجهيز مشارك آخر» يمسح الهوية صراحةً.

كل سيناريوهات Mock تعرض الخانات الخمس نفسها: ESCAPE.EXE بالمعرّف mock، ثم ألعاب QA بالمعرّفات 2 و3 و4 و5. استُبدلت QA 01 ولم يُضف عنصر سادس. النتائج الفعلية تتقدم على نتائج السيناريو لنفس اللعبة؛ المحاولات النشطة لا تُحتسب كإكمال افتراضي. أي نتيجة أو محاولة قديمة بمعرّف خارج الكتالوج، بما فيها 1، تظهر كتعارض يمنع اعتماد المجاميع أو متابعة اللعب دون حذف البيانات أو تحويلها. بيانات Mock مؤقتة وتُمحى عند تحديث الصفحة. أوصاف صفحة الحاوية وزر نتيجة 80 في المراحل أدناه تخص QA؛ تفاصيل دمج ESCAPE.EXE في [دليل تكامل الألعاب](docs/game-integration.md).

## التشغيل المحلي

المتطلبات المعتادة: Node.js 20.9 أو أحدث وpnpm، ومتصفح Chrome لاختبارات الواجهة.

~~~sh
pnpm install --frozen-lockfile
pnpm dev
~~~

افتح http://127.0.0.1:3000 (أو http://localhost:3000).

على جهاز Windows الحالي، إذا لم يكن Node.js مضافًا إلى PATH، يمكن استخدام نسخة Node الموجودة في Codex وهو مفتوح:

~~~powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run.ps1 dev
~~~

الخيار ExecutionPolicy يخص هذه العملية فقط ولا يغيّر إعداد النظام. يدعم السكربت اختيار المسار صراحةً عبر -NodePath، ولا يثبت برامج على الجهاز. أوقف الخادم بـ Ctrl+C.

## تجربة شاشة الوصول — وضع Mock فقط

- الحقل الفارغ: رسالة تطلب إدخال الرمز.
- demo: تأكيد نجاح تجريبي بعد تأخير قصير لمحاكاة الطلب.
- offline: محاكاة فشل الاتصال وإتاحة إعادة المحاولة.
- أي رمز آخر: رفض الرمز.
- زر العين يظهر الرمز أو يخفيه؛ Enter يرسل النموذج.
- أثناء التحقق تُعطّل عناصر النموذج ويُمنع الإرسال المتكرر.
- عند النجاح يُمسح الرمز، والعودة تعيد النموذج فارغًا. تحديث الصفحة يعيد شاشة الوصول.

هذه قيم عرض عامة وليست أسرارًا. لا توجد مصادقة إنتاجية أو جلسة محفوظة أو اتصال بباك إند في وضع Mock.


## تجربة المرحلة الثانية

بعد التحقق بالرمز demo، اختر «تجهيز البوث».

- مشارك جديد: الاسم الكامل ورقم تعريفي رقمي بلا طول ثابت.
- مشارك سابق: الرقم التعريفي فقط؛ جرّب 00123 لبيانات وهمية معلّمة.
- يتم توحيد الأرقام العربية والفارسية إلى 0-9 مع إبقاء الأصفار الأولى.
- يسجّل الـMock البيانات في الذاكرة فقط، ويتيح استرجاعها في نفس الصفحة. تحديث الصفحة يمسح السجلات التجريبية؛ قفل البوث يمسح بيانات الشاشة ويحافظ على سجلات الذاكرة لاستعادة المحاولة.
- الرقم المكرر لا يكتب فوق بيانات المشارك السابق.
- «مسح البيانات»، تغيير نوع المشارك، و«تجهيز مشارك آخر» تفرّغ حقول الشاشة والنتيجة.
- جرّب «محاكاة تعذّر الاتصال» لإظهار الفشل، ثم أزل العلامة وأعد إرسال الطلب. استخدم بيانات وهمية للعرض.

الخدمة في src/services/participant-service.ts، والمحاكاة في mock-participant-service.ts. تستورد الشاشة الخدمة من src/services/index.ts؛ participantDemo أدوات عرض مؤقتة تزال عند اعتماد محول مدى. أنواع النتائج احتياجات محلية وليست عقد API نهائيًا.

## تجربة المرحلة الثالثة

تظهر حالة المشاركة تلقائيًا بعد تسجيل المشارك أو استرجاعه. الأهلية محمّلة من خدمة مستقلة؛ الواجهة تعرض قرار الخدمة وأسباب المنع دون استنتاج أهلية إنتاجية محليًا.

- «إعدادات العرض التجريبي» تتيح اليوم 1 إلى 5 وقسم الطلاب/الطالبات وسجلًا افتراضيًا. هذه أدوات عرض مؤقتة؛ لا تمثل صلاحية تغيير اليوم أو قسم المشارك في الإنتاج.
- الجدول افتراضي بلا تواريخ: لعبة تجريبية برقم اليوم لكل قسم. اليوم الثالث في هذا المثال يتيح اللعبتين 03 و04 للطالبات مقابل 03 للطلاب. هذا ليس تحديدًا لليوم الاستثنائي الحقيقي.
- «شارك اليوم» يمنع جميع الألعاب، حتى لو توفر خياران. «أكمل لعبة اليوم سابقًا» يمنع اللعبة المكتملة فقط. «محاولة قيد التنفيذ» تمنع اختيار محاولة أخرى.
- المجموع يُحسب من النتائج التجريبية المعتمدة فقط، بحد 100 للعبة و500 إجمالًا. إكمال الألعاب الخمس اختياري. سيناريو اكتمال الخمس ينقل العرض إلى اليوم الخامس لتفادي نتائج مستقبلية.
- يمكن اختيار لعبة واحدة ثم تأكيد الاختيار؛ لا يوجد Start أو حجز محاولة أو تشغيل لعبة أو كتابة نتيجة في المرحلة الثالثة.
- عند تغيير اليوم/القسم/السجل أو تحديث الحالة، يُلغى الاختيار السابق. عند تعذر التحميل تختفي الخيارات ويظهر زر إعادة المحاولة؛ لا نفترض الأهلية.
- تجهيز مشارك آخر يمسح لوحة الأهلية والاختيار ويعيد أدوات العرض للقيم الافتراضية.

الملفات: src/features/eligibility/eligibility-panel.tsx، وsrc/services/eligibility-service.ts، وsrc/services/mock-eligibility-service.ts. نقطة الربط src/services/index.ts. اختبارات المرحلة tests/eligibility.spec.ts.

## تجربة المرحلة الرابعة

1. ادخل بالرمز demo، ثم جهّز البوث واسترجع المشارك 00123.
2. اختر لعبة متاحة، وأكد الاختيار، ثم اضغط «ابدأ اللعب».
3. بعد اعتماد الخدمة التجريبية تظهر صفحة اختبار الحاوية داخل المنصة. جرّب «اختبار التفاعل». هذه ليست لعبة ولا ترسل نقاطًا.
4. «طلب مساعدة» ثم «العودة إلى شاشة الموظف» يُبقي المحاولة نشطة؛ استخدم «استئناف المحاولة» لفتحها مجددًا دون حجز جديد.
5. قبل البدء افتح «محاكاة خدمة بدء المحاولة» لتجربة الرفض أو تعذر الاتصال أو حجز المحاولة وفقد الرد. عند فقد الرد استخدم التحقق من الحالة، ولا تفترض النجاح أو تعاود البدء مباشرة.

الـMock يحتفظ بالمحاولات في ذاكرة الصفحة فقط. قفل البوث يحجب بيانات المشارك، وتحديث الصفحة يمسح المحاكاة بما فيها المحاولات. تتوفر محاكاة حفظ النتائج في المرحلة الخامسة الموضحة أدناه.

تفاصيل الربط وحدود صفحة الاختبار: [docs/game-integration.md](docs/game-integration.md). الملفات الجديدة في src/features/games/ وsrc/services/*attempt* وpublic/games/container-check/.

## تجربة المرحلة الخامسة

- بعد تشغيل الحاوية، افتح «اختبار انتهاء المحاولة وحفظ النتيجة»، ثم «إنهاء تجريبي بنتيجة 80».
- هذه أداة اختبار QA في المنصة وليست لعبة أو بروتوكول إنهاء معتمدًا للأقسام. رسائل النقاط من iframe الخاص بـQA تُتجاهل؛ ESCAPE.EXE لها مسار النتيجة الفعلية في Mock وLive عبر خدمات الوضع المحدد.
- قبل الإنهاء يمكن اختيار الطبيعي، تعذر الاتصال، الحفظ مع فقد الرد، أو الرفض.
- لا يظهر نجاح ولا يبدأ العد التنازلي عند الفشل. «إعادة محاولة الحفظ» تستخدم نفس المحاولة والنتيجة، و«التحقق من حالة الحفظ» يسترجع قرار الخدمة.
- بعد تأكيد الحفظ تظهر النقاط 10 ثوانٍ ثم يعود المشارك نفسه إلى اختيار ألعابه، مع تحديث النتائج والأهلية ومنع إعادة اللعبة المكتملة. تبقى الهوية وإعدادات التجربة حتى اختيار «تجهيز مشارك آخر» أو قفل البوث. تظل السجلات التجريبية في ذاكرة الخدمة للاسترجاع، وتمنع النتيجة المحفوظة إعادة اللعب.
- تحديث الصفحة يمسح جميع بيانات Mock. لا توجد استعادة بعد إعادة التحميل حتى يصل Backend.
- ملفات المرحلة: result-screen.tsx وresult-service.ts وmock-result-service.ts؛ نقطة تبديل الخدمة services/index.ts.

## نقطة التوقف

تم تنفيذ محولات Backend ودمج ESCAPE.EXE في Mock وربطها بالمعرّف الرسمي 1 في Live. التحقق من رحلة مستخدم مصادق عليها على Supabase وتجهيز بقية الألعاب لم يكتمل بعد. أُلغي جدول الأقسام وفق التحديث أعلى الملف.

التحقق: نجحت حالات الاختبار الـ25 وفحص TypeScript وبناء الإنتاج. علقت عملية إغلاق خادم التطوير بعد نهاية الحالات وأُوقفت؛ أُعيد تشغيل اختبارات المرحلة الخامسة على خادم الإنتاج للتحقق من الخروج الطبيعي.


## تجربة المرحلة السادسة

- من شاشة البوث الفارغة افتح «لوحة المتصدرين». فتحها يمسح أي إدخال غير مرسل، والعودة تعيد نموذجًا فارغًا.
- تعرض حتى ثلاثة مشاركين بحسب مجموع النتائج المحفوظة فعليًا في Mock؛ لا تحتسب المحاولات النشطة أو السجلات الافتراضية في إعدادات الأهلية.
- بعد إنهاء تجربة وحفظ نتيجتها والعودة تلقائيًا لاختيار الألعاب، اختر «تجهيز مشارك آخر» ثم افتح القائمة لرؤية النتيجة. الأرقام التعريفية لا تظهر.
- حالات التحميل والقائمة الفارغة والفشل واضحة؛ التحديث يخفي القائمة السابقة إلى حين تأكيد أحدث استجابة.
- «إعدادات عرض المتصدرين التجريبية» توفر مثال ثلاثة متصدرين وتعادل، قائمة فارغة وفشل اتصال. المثال منفصل عن النتائج المحفوظة.
- الترتيب العام والتعادل الحاليان للعرض فقط؛ مدى تحدد السياسة النهائية. لا توجد لوحة إدارة.
- تفاصيل الربط المعلقة: [docs/backend-integration.md](docs/backend-integration.md).

آخر تحقق للمرحلة السادسة: اجتازت مجموعة الاختبارات الكاملة 28 اختبارًا على نسخة الإنتاج، ونجح TypeScript وبناء الإنتاج. اختبارات الربط مع Backend الحقيقي معلقة إلى وصول التفاصيل.


## إعداد وضع الاتصال والاختبارات

- يجب تحديد NEXT_PUBLIC_API_MODE صراحةً: mock للمحاكاة أو live للخدمة. القيمة المفقودة أو الفارغة أو غير المعروفة تعرض خطأ إعداد وتمنع أي طلب Backend؛ لا يوجد وضع Live افتراضي.
- عند اختيار live يجب تحديد NEXT_PUBLIC_API_BASE_URL صراحةً لعنوان API المعتمد للبيئة المطلوبة. لا يوجد عنوان Production أو Staging افتراضي. اختيار live لا يثبت سلامة الاتصال بالخدمة.
- يقبل العنوان HTTPS، أو HTTP على loopback للاختبار المحلي فقط. تُرفض العناوين النسبية وبيانات المستخدم وكلمات المرور وquery وfragment والصيغ التي تتطلب تصحيحًا ضمنيًا. لا تظهر قيمة الإعداد في رسالة الخطأ.
- الإعداد الصالح لا يثبت أن الوجهة Staging؛ تؤكد Mada عنوان المشروع وعزل قاعدة بياناته والدوال والمهاجرات وCORS قبل أي اتصال فعلي.
- NEXT_PUBLIC_* تُدمج أثناء البناء. ابنِ Mock وStaging بصورة منفصلة؛ تغيير Runtime Environment أو إعادة تشغيل حزمة قديمة لا يغيّر وجهتها. أعد تشغيل خادم التطوير بعد تغيير الإعدادات.
- ملفات .env المحلية وإعدادات البناء الخارجية قد تغير الوجهة؛ راجع أولوية إعدادات Next.js. ملف .env.staging لا يُحمّل تلقائيًا كوضع مستقل، ولا تستخدم NODE_ENV=staging.
- لا تضع رمز البوث أو signing secret أو Service Role في أي متغير عام. يُدخل رمز الوصول في الشاشة فقط.

مثال PowerShell لبناء Mock:

~~~powershell
$env:NEXT_PUBLIC_API_MODE = 'mock'
pnpm build
~~~

لبناء Staging لاحقًا بعد اعتماد البيئة: اضبط NEXT_PUBLIC_API_MODE=live وNEXT_PUBLIC_API_BASE_URL إلى عنوان Edge Functions الذي تؤكده Mada ثم نفّذ build في مساحة منفصلة. لا تستخدم حزمة Mock نفسها ولا تنقل حزمة Production القديمة مع تغيير runtime فقط.

### اختبارات محلية بلا خدمات حقيقية

~~~powershell
$env:NEXT_PUBLIC_API_MODE = 'mock'
pnpm test
$env:NEXT_PUBLIC_API_MODE = 'live'
pnpm test
~~~

Playwright يفرض وضعًا صريحًا ويشغّل خادمًا محليًا جديدًا: 3101 لـMock و3102 لـLive، دون إعادة استخدام خادم قائم. عنوان API الاختباري وهمي على backend.invalid؛ لا يُستخدم عنوان المشغّل الحقيقي حتى لو كان موجودًا في البيئة.

الخادم يعمل على نسخة مؤقتة داخل tmp/ ولا ينسخ .env أو incoming-games أو مخرجات البناء. هذا يحمي next-env.d.ts الأصلي من تحديثات Next.js. عمليات Node محمية بحاجز loopback، والمتصفح يستخدم proxy محليًا لا يمرّر الاتصالات الخارجية، مع حظر Service Workers واعتراض الشبكة وWebSocket. الطلب غير المحاكى يُحظر ويُفشل الاختبار. تستخدم الحالات tests/fixtures بدل استيراد test مباشرة من @playwright/test، وللسياقات الإضافية تستخدم newIsolatedContext.

اختبارات Live تستخدم عنوان API الاختباري المركزي في tests/test-environment.ts، ولا تعتمد على hostname خاص بـProduction. فحوص العزل تتحقق كذلك من طلب API غير محاكى ومحاولة تجاوز الاعتراض. هذه اختبارات عقود وواجهة محلية، وليست اختبار تكامل Supabase.

لتحقق بناء معزول وآمن دون تعديل ملفات Next المولدة في الجذر:

~~~powershell
node scripts/run-isolated-next.mjs build mock
node scripts/run-isolated-next.mjs build live
~~~

كلاهما يستخدم إعدادًا وهميًا وحاجز شبكة Node؛ مخرجاتهما داخل tmp/ وليستا حزمتين للنشر إلى Staging.

تسجيل المشارك واسترجاعه يرفضان student_number المرتجع إذا لم يطابق الرقم المطلوب حرفيًا قبل تحديث الذاكرة؛ لا تُحذف أصفار ولا تُوحّد هويات مختلفة داخل المحول. يبقى تطبيع إدخال المستخدم الحالي في واجهة النموذج كما هو.

ملفات الربط الأساسية: backend-client.ts وbackend-services.ts وplatform-session.ts وruntime-config.ts داخل src/services، وsession-renewal.tsx داخل src/features/access.

آخر تحقق بعد الربط: 9 اختبارات API/واجهة باعتراض الشبكة + 28 اختبار Mock نجحت، وبناء الإنتاج وفحص TypeScript ناجحان. وضع المعاينة النهائي live؛ التحقق المصادق عليه من Supabase لم يُنفذ دون رمز البوث.

## Dev Run — Live game 2

Dev Run منشورة في public/games/dev-run/ من incoming-games/Dev--Run.zip. يبقى ZIP الأصلي وREADME المنسوخ دون تعديل؛ سجل البصمات والتغييرات في docs/dev-run-provenance.md.

تعمل في Live بالمعرّف 2 فقط. ESCAPE.EXE تبقى 1، وLive 4–5 محجوبة. كتالوج Mock لم يتغير: mock لـESCAPE.EXE و2–5 لأصول QA؛ لا يُعاد تفسير سجل QA 2 على أنه Dev Run.

مصافحة Dev Run هي ai-hub:dev-run-init بالإصدار 1، مع game=dev-run وnonce جديد وMessagePort. تُفحص نافذة الأب وأصلها وnonce المطابق للتحميل؛ معامل URL وحده لا يفعّل وضع المنصة. الجاهزية ai-hub:dev-run-ready والقفل ai-hub:dev-run-lock عبر MessageChannel. تبقى sandbox=allow-scripts دون allow-same-origin، ولا تدخل هوية المشارك أو attempt_id أو token إلى iframe.

في وضع المنصة ترسل DEV_RUN_FINAL_SCORE مع version وgame وnonce وscore وmaxScore=100 وstats وbreakdown. يتحقق dev-run-result.ts من الدرجة الصحيحة 0–100 ومن اتساقها مع ScoreManager.compute الأصلي: عناصر حتى 30، أسئلة حتى 50، مكافأة عدم الاصطدام 10 عند الإكمال، ومكافأة الإكمال 10. تُقفل أول نتيجة صحيحة تزامنيًا؛ attempt_id من المضيف فقط.

بعد الإكمال داخل المنصة يُمنع start وgoHome وresetSession وresume وinit وstartLoop ومسار تغيير الحالة من إعادة الجولة. تبقى شاشة النتيجة الأصلية ظاهرة، وتصبح غير تفاعلية، مع استمرار حفظ المنصة خارج iframe. التشغيل المستقل يحتفظ برسالة النتيجة القديمة والإعادة العادية.

المؤقت الأصلي 120 ثانية من اللعب، متوقف أثناء الأسئلة والإيقاف المؤقت؛ قد تتجاوز الجولة 180 ثانية فعلية. لا تفرض المنصة مهلة لعب جديدة. الاستئناف يفتح iframe وnonce جديدين من البداية وبنفس محاولة Backend، دون Start ثانٍ أو استعادة موضع.

تستخدم Start/Progress/Finish وخدمة النتائج واللوحة الموجودة: لا endpoints أو حقول Backend جديدة. يبدأ عد العودة لعشر ثوانٍ بعد تأكيد الحفظ فقط، ويعود المشارك نفسه مع تحديث أهليته. تحذير المغادرة لا يضمن استرداد درجة غير محفوظة بعد إغلاق الصفحة.

التحقق محلي فقط عبر عزل Phase 6B واستجابات Backend معترضة. tests/dev-run.spec.ts وtests/dev-run-results.spec.ts تغطيان الأصل والمصافحة والدرجات والإعادة والمؤقت؛ tests/backend-dev-run.spec.ts تغطي Start والاستئناف وrefresh وFinish وحالات عدم التأكد والعودة والمتصدرين. لا يعني ذلك التحقق من Supabase فعليًا.

قبل اختبار Staging: تؤكد Mada سجل اللعبة 2 وتفعيله وحده الأعلى 100، وتوفر البيئة المنفصلة والمهاجرات والدوال والمصادقة وCORS وعنوان API المعتمد. لا تُستخدم بيانات Production أو رموز فعلية في الاختبارات المحلية.
